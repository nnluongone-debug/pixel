# Firebase setup (accounts + cloud sync)

Pixel Quest runs fully offline as a guest. Signing in (email + 6-digit code)
links the local SQLite data to an account and syncs it to Firestore.

## What is already configured

| Item | Value |
|---|---|
| Firebase project | `habitpixel-309ee` (HabitPixel) — `.firebaserc` |
| iOS app | `com.nnluong.pixelquest` → `ios/Runner/GoogleService-Info.plist` |
| Android app | `com.pixelquest.pixel_quest` → `android/app/google-services.json` |
| Dart options | `lib/firebase_options.dart` (generated by `flutterfire configure`) |
| Firestore | `(default)` database in `asia-southeast1`; rules `firestore.rules` (deployed) |
| Functions | `functions/` — `requestLoginCode`, `verifyLoginCode` in `asia-southeast1` |

Regenerate the app config after adding a platform or changing a bundle id:

```bash
PATH=/usr/local/opt/ruby/bin:$PATH \
GEM_HOME=/usr/local/Cellar/cocoapods/1.16.2_2/libexec \
~/.pub-cache/bin/flutterfire configure --project=habitpixel-309ee \
  --platforms=ios,android --ios-bundle-id=com.nnluong.pixelquest \
  --android-package-name=com.pixelquest.pixel_quest \
  --out=lib/firebase_options.dart --yes
```

(`flutterfire` needs the `xcodeproj` gem; the system Ruby doesn't have it.)

## One-time console steps (project owner)

1. **Blaze plan** — Cloud Functions require it. Console → Usage and billing →
   Modify plan → Blaze. Add a small budget alert.
2. **Authentication** — Console → Authentication → *Get started*. No sign-in
   provider needs enabling: the backend issues custom tokens.
3. **Resend** — create an account at resend.com and an API key with
   *Sending access*. Without a verified domain Resend only delivers to the
   Resend account's own address; verify a domain and set `RESEND_FROM` to send
   to anyone.

## Deploy

```bash
firebase functions:secrets:set RESEND_API_KEY      # paste the key when asked
# optional sender (verified domain):
echo 'RESEND_FROM="Pixel Quest <login@your-domain>"' > functions/.env.habitpixel-309ee
firebase deploy --only functions,firestore
```

If `verifyLoginCode` fails with a `signBlob` / permission error in the logs,
grant the Functions runtime service account the *Service Account Token
Creator* role (IAM) so it can mint custom tokens.

## Data model

- `users/{uid}` — profile: `email` (from the verified sign-in, read-only in
  the app), `name`, `birthYear`, `gender`, `address`, `updatedAt`.
- `users/{uid}/habits/{id}`, `users/{uid}/checkIns/{id}` — mirrors of the
  SQLite rows (camelCase) + `updatedAt` (epoch ms) + `deleted`; deletions are
  tombstones. `user_stats` is never synced: it is recomputed from check-ins.
- `loginCodes/{sha256(email)}` — pending codes (hashed), server-only, TTL on
  `expiresAt`.

## Sync rules of thumb

- SQLite is the source of truth; every local write also queues a row in
  `sync_outbox` (same transaction). Push uploads the outbox, pull applies
  remote docs newer than the last watermark (last-write-wins on `updatedAt`).
- First sign-in on a device uploads the existing guest data to the account.
- Signing out uploads pending changes (best effort), then clears local data
  back to an empty guest.
